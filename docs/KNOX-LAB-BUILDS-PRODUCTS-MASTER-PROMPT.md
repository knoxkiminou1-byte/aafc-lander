# Known verified build

The prior completed KNOX LAB contained four working proof systems:

## 1. Explainable Lead Qualification
A deterministic/explainable lead-scoring system with a required human approval gate before export or downstream action.

The point is not just scoring. A reviewer should be able to see **why** a lead received its score and where human approval enters the workflow.

## 2. Marketing Analytics
A working marketing/campaign analytics experience with validated CSV import and useful dashboard interpretation.

This must remain a real analytical interface, not a decorative chart mockup.

## 3. Crescent Atlas
A searchable New Orleans creative-business data map.

The prior version used the official **City of New Orleans Active Occupational Licenses** dataset and included 18 records with explicit source and interpretation caveats. Preserve provenance and caveats. Never imply the sample is a complete directory of New Orleans businesses.

## 4. Agent Trace
A transparent, scenario-tested agent workflow that exposes its steps, decisions, checks, and handoff logic instead of hiding everything behind a magic-chatbot interface.

The purpose is to demonstrate auditable workflow design and responsible automation.

# Recovery workflow

When a candidate archive/worktree is found:

1. **Inspect without overwriting anything.**
2. Record exact path, size, timestamps, and hash where practical.
3. If archive: unpack into a safe temporary directory first.
4. Identify repository root, current branch, HEAD, remotes, staged/unstaged/untracked changes.
5. Preserve all local changes before switching branches or applying patches.
6. Compare the recovered implementation against the known four KNOX LAB systems and original docs/screenshots.
7. Confirm `/lab` is present and the four systems are functional.
8. Run install/build/typecheck/tests using the repo's actual package manager and documented scripts.
9. Run asset validation.
10. Run browser QA on desktop and mobile.
11. Capture fresh screenshots/evidence.
12. Only after verification, place the work on a safe branch such as `agent/portfolio-max` or a new clearly named recovery branch.
13. Push the branch and create a reviewable PR.
14. Do not merge or deploy until the real production mapping for `kiminouknox.com` is confirmed.
15. After deployment, verify the public `/lab` route, navigation, responsiveness, console, and links.

Never force-push, rewrite history, delete another branch, or discard local work just to make the repository look clean.

# Design modernization direction

The recovered functionality and proof architecture outrank any aesthetic refresh. **Preserve the verified systems first.** Then modernize the presentation if the current BUILDS & PRODUCTS design language is materially stronger.

The intended visual character is premium technical/editorial rather than generic SaaS or AI-demo styling:

- cinematic dark foundation
- restrained high-tech atmosphere
- soft depth/glow rather than neon overload
- strong typography and information hierarchy
- refined glass / translucent panels only where readability remains excellent
- rounded, deliberate dashboard surfaces
- subtle animated borders or motion where they clarify state
- polished data visualization
- sophisticated responsive mobile behavior
- serious enough for clients, recruiters, fellowships, and technical reviewers
- no childish robot imagery
- no random purple-gradient AI template look
- no visual effect that interferes with dashboard readability

Use the **newest canonical design guidance from AAFC BUILDS & PRODUCTS** when it improves this direction. Do not mechanically recreate an older aesthetic simply because it existed in the historical version.
